## 2. Format recommendation — **PDF is the right attachment**

### Verdict: **Attach a PDF.** Keep an HTML version *on* the portfolio, but the file you attach/send is PDF.

| Criterion | **PDF (attach this)** | HTML (host, don't attach) |
|---|---|---|
| ATS parsing | ✅ Standard, reliably parsed when text-based | ⚠️ Inconsistent; many ATS choke on a raw page/URL |
| Email / upload as a single file | ✅ One portable file | ❌ Not a single attachable artifact |
| Opens everywhere, offline, unchanged | ✅ Renders identically for everyone | ⚠️ Depends on hosting, browser, network |
| Print / archive | ✅ Print-perfect, version-locked | ⚠️ Needs a print stylesheet |
| Recruiter pipeline fit | ✅ What recruiters expect to drop into an ATS | ⚠️ Extra friction |
| Interactive / linkable / analytics | ⚠️ Static (use clickable links inside it) | ✅ Strengths — but that's what the **portfolio** already is |

**Why PDF wins for the *attachment*:** recruiters and ATS expect a single, portable, parseable file; PDF is universal, offline-safe, print-perfect, and version-locked. Your **HTML strength already lives in the portfolio site** — duplicating it as the resume format adds hosting/ATS friction without adding value.

**Best practice — do both, from one source:**
1. **Primary deliverable:** a clean, text-based, ATS-friendly **PDF** (selectable text, standard section headings, no multi-column tables in the body, embedded clickable links to portfolio + LinkedIn + the two case studies).
2. **Living version:** a `/resume` **HTML page on the portfolio** with a prominent **"Download PDF"** button (ties directly into the portfolio review's P0-3 "add a résumé" item).
3. Generate both from **one Markdown/source file** so they never drift (see §3).

> ⚠️ Avoid exporting the PDF as a flat image (e.g., "export frame as PDF" from Figma with no text layer) — that breaks ATS parsing. Keep the text selectable.
